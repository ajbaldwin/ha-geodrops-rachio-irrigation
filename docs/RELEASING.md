# Releasing

This repo does not contain the scheduler itself. It vendors a versioned
snapshot of the scheduler ("the brain") from its own canonical repo into
`custom_components/geodrops_rachio/bundled_app/`, wraps it with a Home
Assistant config flow + entities, and ships the result as a HACS-installable
integration.

Every release therefore has **two independent version stamps** — keep them
straight, because they answer different questions:

| Stamp | Where | What it versions | What changing it affects |
|---|---|---|---|
| `manifest.json` `"version"` | `custom_components/geodrops_rachio/manifest.json` | This wrapper's own Python (config flow, entities, `delivery.py`, `updater.py`, ...) | What HACS shows the user, and whether HACS/HA flags the update as needing a restart |
| `bundled_app/VERSION` | `custom_components/geodrops_rachio/bundled_app/VERSION` (generated by `vendor_scheduler.py`, copied from the scheduler repo's own `VERSION` file) | The vendored scheduler brain | Whether `delivery.py` decides the pyscript app + `irrigation_lib` need to be re-copied and `pyscript.reload`'d on the next config-entry setup/reload |

A release that only re-vendors a newer scheduler snapshot (bundled `VERSION`
changes, no wrapper `.py` files touched) is picked up by already-running
installs **with no Home Assistant restart**: `updater.py` listens on the
HACS update entity, reloads the config entry when it changes, and
`delivery.py` re-reads `bundled_app/VERSION` from disk, sees it differs from
the `.geodrops_rachio_version` stamp in the user's pyscript directory, copies
the new script + library, and calls the `pyscript.reload` service — all
without needing HA to re-import any Python module.

A release that changes any file under `custom_components/geodrops_rachio/`
itself (config flow, platforms, `delivery.py`, `updater.py`, etc.) needs a
**Home Assistant restart** after HACS installs it, same as any other custom
integration update — Python modules already imported by HA are not
re-executed by a config-entry reload, only by a full restart.

**Messaging rule — do not advertise "no restart."** HACS shows a "restart
Home Assistant" prompt after *every* download, regardless of what changed: it
replaces the whole integration folder and sees the manifest bump, and cannot
tell a brain-only vendor from a wrapper-Python change. The brain-only
auto-apply above is real, but a user still sees the prompt — so a release note
that claims "no restart needed" only confuses. Never make that claim in
release notes or the CHANGELOG. Call out a restart **only** when wrapper
Python changed (then it is genuinely required); for a brain-only release, say
nothing about restarts.

**Always bump `manifest.json`'s version for every release**, even a
brain-only vendor bump — HACS uses it (together with the git tag/release) to
know a new version exists at all. The manifest version bump does not by
itself trigger anything in `delivery.py`; that logic only looks at
`bundled_app/VERSION` vs. the on-disk stamp.

## Release steps

1. **Vendor the current scheduler snapshot.** From the root of this repo,
   run:

   ```bash
   python tools/vendor_scheduler.py <path-to-scheduler-repo> custom_components/geodrops_rachio
   ```

   `<path-to-scheduler-repo>` is a local checkout of the canonical scheduler
   repo. This:
   - reads `pyscript/apps/irrigation/__init__.py` from that repo,
     rewrites its `@state_trigger("input_button.irrigation_stop")` to
     `@state_trigger("button.geodrops_rachio_stop")` (the integration's own
     stop button), and writes the result to
     `custom_components/geodrops_rachio/bundled_app/geodrops_rachio.py`;
   - copies `pyscript/modules/irrigation_lib/` from that repo to
     `custom_components/geodrops_rachio/bundled_app/irrigation_lib/`,
     replacing whatever was there;
   - reads the scheduler repo's own `VERSION` file and stamps it into
     `custom_components/geodrops_rachio/bundled_app/VERSION`.

   The transform aborts loudly if the canonical app's stop-trigger line has
   changed shape — that means the scheduler's app layout moved and the
   transform in `tools/vendor_scheduler.py` needs updating before you can
   vendor again.

2. **Run the test suite.**

   ```bash
   bash tools/test.sh
   ```

   On Windows, `pytest-homeassistant-custom-component` cannot run natively
   (it imports the Unix-only `fcntl`), so `tools/test.sh` runs the tests
   inside a Linux Docker container instead of your host Python. Build the
   image once (or after `Dockerfile.test`/`requirements_test.txt` change)
   with:

   ```bash
   docker build -f Dockerfile.test -t geodrops-test .
   ```

   `tools/test.sh` mounts the repo into that container and runs `pytest`
   (any arguments you pass it are forwarded to `pytest`). CI (`.github/workflows/ci.yml`)
   runs the same suite with plain `pytest` on `ubuntu-latest`, so a container
   rebuild only affects your local run, not CI.

3. **Bump the wrapper version.** Edit `custom_components/geodrops_rachio/manifest.json`
   and increment `"version"`. Do this on every release, per the table above,
   regardless of whether this release touched wrapper `.py` files or only
   re-vendored the brain.

4. **Commit.**

   ```bash
   git add custom_components/geodrops_rachio/bundled_app custom_components/geodrops_rachio/manifest.json
   git commit -m "release: vX.Y.Z"
   ```

   (Add any other changed files from this release to the same commit as
   appropriate.)

5. **Write the release notes.** HACS shows the GitHub release **body** as the
   changelog for that version, so it is how users see what a pending update
   contains before they install it — always write real notes, never
   `--generate-notes` (a raw commit list). Keep them short and user-facing:
   what changed and what got fixed. Mention a restart **only** when wrapper
   Python changed; never claim a release skips the restart (see the messaging
   rule above and the sanity check below). Add the same summary as a new top
   section in `CHANGELOG.md` so the history lives in the repo too.

6. **Tag and release** from `main`.

   ```bash
   git tag vX.Y.Z
   git push origin main vX.Y.Z
   gh release create vX.Y.Z --title vX.Y.Z --notes-file <notes.md>
   ```

   (Or pass `--notes "..."` inline.) HACS installs updates from GitHub
   releases, so the release is what makes the new version — and its notes —
   visible to users' HACS instances; the `manifest.json` bump alone does not
   distribute anything. Because `hacs.json` sets `hide_default_branch`, HACS
   only ever offers tagged releases, not raw `main`.

## Sanity check before tagging

- `custom_components/geodrops_rachio/bundled_app/VERSION` matches the
  scheduler repo's `VERSION` at the commit you vendored from.
- `custom_components/geodrops_rachio/manifest.json`'s `"version"` was bumped.
- `bash tools/test.sh` passes.
- If you touched any wrapper `.py` file in this release, mention in the
  release notes that it requires a Home Assistant restart after updating. For a
  brain-only re-vendor, say nothing about restarts — do NOT claim it needs no
  restart (HACS prompts one regardless; see the messaging rule above).
